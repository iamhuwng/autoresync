# Notification recovery scheduler budget

Checked against source on 2026-09-25. The release candidate config has one `*/2 * * * *` trigger and `NOTIFICATION_RETRY_BATCH=class-homework`. It rotates class membership, homework submission, manual homework reminder, and homework reset retries, one bounded family every two minutes. Each first-batch family is visited every eight minutes, including the two action routes exposed in the selective Hosting artifact. The full-family stage requires a separate config change to `NOTIFICATION_RETRY_BATCH=all` plus a `* * * * *` bulk trigger. The full schedule below has three bulk families and 14 small-family slots, including two each for class and homework submission; both triggers can fire on even minutes.

| Queue | Maximum interval between its passes | Maximum delay after a one-hour retry due time |
|---|---:|---:|
| Course announcement, THCS homework, session | 3 minutes | 3 minutes |
| Class and homework | 20 minutes | 20 minutes |
| Other small families | 28 minutes | 28 minutes |

For a 30-recipient bulk event at 10 recipients per pass, an immediate first pass leaves two Cron passes, so nominal completion is within 6 more minutes when the backend is healthy. A 500-recipient session takes up to 150 minutes if it waits for Cron from the start. The configured 1,000-recipient announcement ceiling takes up to 300 minutes on the same assumption. Busy queues add delay; there is no per-student polling loop. Failed recipient batches become due for one retry about one hour after the initial pass finishes.

The first stage invokes the Worker 720 times per UTC day and uses one Cron slot. The full stage invokes it 1,440 + 720 = 2,160 times per UTC day, 2.16% of the Workers Free 100,000-request daily limit, and uses two of the account's five Cron slots. The source caps a bulk invocation at 10 recipients and a small-family due scan at one to three intents. On even minutes both full-stage triggers fire as **separate invocations**, so the per-invocation subrequest and CPU limits apply independently while both count toward the daily request limit.

The THCS Firestore store shares the RTDB client's OAuth token, whose scope includes Firestore, instead of signing and exchanging a token on every Firestore request. The manual reminder and homework reset stores now use that same cached token path; a focused Workerd check observes one OAuth exchange per store across an empty due scan and follow-up Firestore read. Another focused Workerd test measures **23 external fetches** for an empty THCS due scan plus ten inbox creates: one OAuth, one Firestore query, one RTDB queue query, ten idempotency reads, and ten inbox writes. Source-path accounting for a ten-recipient scheduled pass gives 29 requests for course announcements with a terminal admin issue, 30 for sessions with a terminal admin issue, and up to **41 for THCS homework** with a class roster, terminal issue, and all three conditional-write attempts on both Firestore intent updates. These are no-redirect counts. Cloudflare Free currently allows 50 external subrequests and 10 ms CPU per invocation. Redirects count as extra subrequests. [Cloudflare Workers limits](https://developers.cloudflare.com/workers/platform/limits/), [Cron Trigger handler](https://developers.cloudflare.com/workers/runtime-apis/handlers/scheduled/).

The populated **first-batch** Workerd check executes each real retry handler and store against mocked Firebase HTTP with two due intents. It measures 18 external requests for successful class membership delivery, 11 for terminal homework submission failure, and 10 each for terminal manual-reminder and homework-reset failure. The homework path uses two OAuth exchanges because its Firestore query and RTDB failure reporter own separate token clients. These checks cover one path per family; Cloudflare CPU, redirects, and other populated branches remain unmeasured. Local elapsed timing is not a substitute for Cloudflare invocation CPU readback.
