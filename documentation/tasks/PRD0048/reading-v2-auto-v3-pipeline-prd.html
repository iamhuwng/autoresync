PRD-0048 Reading V2 Auto V3

Gemini marks topology. Groq normalizes question areas. Local code owns truth.

This product requirement document defines the new Reading V2 Auto import pipeline for IELTS Reading Clippings sources. The goal is simple: convert one messy raw test into a complete Studio draft without silent passage loss, question loss, answer-key drift, or unsafe projection leakage.

  • InputOne raw IELTS Reading source pasted into Auto.
  • GeminiOne full-source marker call returns line coordinates and answer-key rows.
  • GroqThree per-passage question-area calls, preferably on three distinct keys.
  • OutputStudio draft, or fail-closed diagnostics. No silent partial import.

1. Product Summary

Reading V2 Auto must stop treating provider JSON as canonical. AI is used only where it is strong: recognizing messy document structure and normalizing inconsistent question formatting. Local code owns exact source slices, canonical V2 objects, answer-key binding, validation, diagnostics, and publish readiness.

3 passage packages

Each package means one passage body plus its own question area and answer rows.

40 question numbers

Supported full tests must cover the complete IELTS Reading question range.

1 Gemini marker call

Gemini sees full source, but returns only coordinates and normalized key rows.

3 Groq package calls

Groq sees question areas only, preferably distributed across three key slots.

Core invariant: AI handles messy formatting. Code owns exact source, canonical parse, answer binding, validation, and trust.

3. Data Ownership And Boundaries

This is the main safety improvement. Provider output can guide local code, but it cannot become source truth.

Local Code Owns

  • Raw source and line index
  • Passage body text
  • Three package construction
  • Canonical V2 IDs
  • Answer binding and scoring rules
  • Publish readiness

Gemini Can Return

  • Passage body start/end lines
  • Question-area start/end lines
  • Question-group range hints
  • Task-type hints
  • Pollution/exclusion spans
  • Normalized answer-key rows

Groq Can Return

  • Strict question transcript
  • Confirmed task type
  • Instruction metadata
  • Exact copied question text
  • Reference banks and options
  • Ambiguity diagnostics

Never Allowed

  • Groq receives passage body text
  • AI solves or invents answers
  • AI creates final Studio IDs
  • Partial draft is silently accepted
  • Raw diagnostics leak to student runtime
  • Provider text bypasses verifier

4. Groq Package Fan-Out

Existing Groq behavior is round-robin plus fallback. V3 needs a stronger contract: plan three package jobs, reserve available key slots, run distinct keys in parallel when possible, and retry only failed packages.

Package 1

Q1-13 question area only. Passage body stays local.

>

Groq key slot 0

Reserved before call. Fingerprint only in diagnostics.

>

Transcript 1

Strict groups, questions, banks, layout targets.

Package 2

Q14-26 question area only. Includes marker hints and answer rows.

>

Groq key slot 1

Runs independently from package 1 and package 3.

>

Transcript 2

If this fails, only package 2 retries.

Package 3

Q27-40 question area only. No full test dump to Groq.

>

Groq key slot 2

Falls back only if the package's assigned key fails.

>

Transcript 3

Successful packages are preserved during repair.

Planning Rules

Before Groq calls, the fan-out service must list non-benched key slots and create package plans.

  • If 3+ keys are available, assign different keys to package 1, 2, and 3.
  • If fewer keys are available, degrade to bounded round-robin with visible diagnostics.
  • If a key fails, bench it using existing cooldown rules and retry that package on another key.
  • Raw key values must never appear in logs, diagnostics, reports, or Studio.

6. Provider Contracts

Actor Input Output Forbidden Local Verification
Gemini marker Full numbered raw source lines. Line ranges, group hints, pollution spans, answer-key rows. Full passage copies, canonical IDs, publish readiness, answer solving. Every line span exists, ranges do not overlap, expected questions and answer rows are covered.
Local package splitter Verified marker coordinates and raw source. Three exact passage packages with local passage body and Groq question input. Trusting unverified provider spans. Package hashes, source slices, excluded pollution, question ranges.
Groq normalizer One passage question area plus marker hints and relevant answer rows. Strict transcript with task type, instruction metadata, exact question/bank/layout text. Passage body text, answer reasoning, paraphrase, invented text, final Studio prose. Every copied text field appears in the question area; every expected question appears once.
Local assembler Passage package, Groq transcript, answer rows. Canonical V2 passage, groups, interactions, scoring rules. Provider-owned IDs or unbound answer rows. Draft coverage, scoring validity, projection safety, Studio readiness.

7. Failure Gates And Recovery

The pipeline fails small. It reports the exact broken unit and keeps successful units when safe.

  • Marker failure Missing passage span, impossible line range, overlapping question area, or answer rows outside source.
  • Package failure Package cannot reconstruct exact local passage body or question area from verified line ranges.
  • Groq failure Key rate limit, invalid key, transcript missing a question, transcript paraphrases source text, or task type conflicts with cues.
  • Assembler failure Duplicate question numbers, unbound answer rows, missing scoring rule, invalid layout target, or unsafe projection field.
  • Repair scope Retry only the failed package when Groq fails. Re-run Gemini only when marker verification fails or raw source changes.
  • Studio result Studio receives either a complete guarded draft or classified fail-closed diagnostics. No silent partial import.
