  Executive Summary

  Verdict: NEEDS POLISH (close to ready for Part 2; PRD-0054 needs more reconciliation).

  The three PRDs are coherent in intent and the two tasklists are unusually disciplined (explicit anchors, ambiguity
  flags, stop-and-record gates). The core architecture decision — composition-first ref-only masters with single-passage
  Studio editing — is sound and matches the Codex planning sessions. However, there are real, verified conflicts and
  gaps that a junior would implement inconsistently:

  1. The central premise is verified true: the publish pipeline still embeds the full ReadingV2Document (TeacherLobby
  routes all Reading V2 masters to full-test Studio), so Part 2 is genuinely needed — but Part 1's tasklist already
  marks extraction/composition publish as done ([x]), creating a "is it built or not?" contradiction that must be
  resolved before coding.
  2. Several cross-PRD rule conflicts (mixed Test Types allowed at creation vs. same-Test-Type forced at repair;
  auto-update-master-ref on remake vs. Update-References-modal on edit; duplicate guard scope).
  3. Underspecified mechanics that block safe implementation: cross-passage numbering derivation, the authoritative
  "student started" signal, where the frozen composed projection is stored and how it stays consistent across
  RTDB/Firestore, and audit-inside-atomic-publish vs. the existing fire-and-forget auditService.

  None are fatal. All are fixable with PRD edits before implementation.

  High-Severity Issues

  H1. "Already built" vs. "not built" contradiction on composition publish

  - Issue: Part 1 tasklist marks 5.0/6.0 (extraction + composition-first publish + rollback) [x] done; Part 2 treats it
  as not-yet-built.
  - Evidence: tasks-0052…library.md lines 304–351 all [x]. readingV2PublishPipeline.service.ts still carries document:
  through writes (verified). handleEditTest (TeacherLobbyPage.jsx:891–907) routes every Reading V2 material to
  TEACHER_READING_V2_REVISE with no published/draft branch.
  - Why it matters: A junior reading Part 1 will assume publish is composition-first and skip Phase 2; a junior reading
  Part 2 will rebuild it. Both are wrong without inspecting code.
  - Affected: Part 1 tasklist 5.0/6.0; Part 2 §1.4, §3.3–3.6, Phase 0/2.
  - Correction: Add a Part 2 §1.4 statement: "Part 1 added additive extraction/composition writes but did NOT remove
  embedded document payload and did NOT split Edit routing; Part 2 supersedes by making master writes ref-only and
  branching Edit by publish state." Keep the Phase 0 verification gate but state the expected current truth.

  H2. Edit routing has no published-vs-unpublished branch (core behavior change)

  - Issue: Part 2 requires Edit Test on a published master → Edit Test Modal, but unpublished drafts still use full-test
  Studio. Current code has a single unconditional branch to Studio.
  - Evidence: TeacherLobbyPage.jsx:893–906 — if (readingV2MaterialId) { navigateTo('TEACHER_READING_V2_REVISE') }. No
  publish-state check.
  - Why it matters: The entire Part 2 / PRD-0054 repair model hinges on this branch. The PRD never states how publish
  state is determined for a Lobby row (is there a published flag, a publishedVersionId, a state field on the listing
  row?). A junior will guess.
  - Affected: Part 2 §3.7, FR-MASTER-EDIT-1/2; tasklist Phase 3.
  - Correction: Add an FR defining the exact field the Lobby row uses to decide published vs. draft (e.g.,
  publishedVersionId != null or state === 'published'), and define behavior for a master that has both a published
  version and an open draft revision.

  H3. Cross-PRD conflict: mixed Test Types allowed at creation, forbidden at repair

  - Issue: Part 2 FR-EXISTING-19 (and decision 41) allows mixed Test Types with warning. PRD-0054 FR-STUDIO-ADD-2 says
  the add-existing picker "must require the same Test Type."
  - Evidence: Part 2 line 423 vs. PRD-0054 lines 384, 394. The Codex review session (2026-06-09, rollout-…08-06-29)
  explicitly flagged this as unresolved ("strict same-type only, or compatible mismatch with confirmation?") and the
  decision was compatible mismatch with confirmation.
  - Why it matters: Same composition object, two contradictory validation rules depending on entry path. A repaired
  master could be forced stricter than a created one.
  - Affected: PRD-0054 §7.7 FR-STUDIO-ADD-2/7; Part 2 §7.7.
  - Correction: Align both to the recorded decision: allow Test Type mismatch with explicit teacher confirmation +
  warning, not a hard block. Edit FR-STUDIO-ADD-2 to "should default to same Test Type; mismatch requires confirmation."

  H4. Conflict: remake auto-updates master ref vs. passage-edit shows Update-References modal

  - Issue: Two different "passage published → ref update" semantics. PRD-0054 §2.7 + decision 34 + FR-STUDIO-REMAKE-7:
  single-passage Studio publish atomically updates the originating master ref. Part 2 FR-PASSAGE-STUDIO-6/8 +
  FR-UPDATE-REFS: publishing a passage version must not mutate masters; show Update references? (default unchecked).
  - Evidence: PRD-0054 line 138, 424 vs. Part 2 lines 315–325, 154 (decision 14).
  - Why it matters: When a teacher remakes a broken passage from a master, does the master ref auto-update (0054) or
  wait for the Update-References modal (Part 2)? Junior will implement one and break the other flow. Also "atomic across
  the new passage publish + master ref update" spans two materials — needs transaction definition.
  - Affected: PRD-0054 §2.7, §7.9 FR-STUDIO-REMAKE-7; Part 2 §7.4/§7.5.
  - Correction: Carve the two cases explicitly: (a) broken-ref remake → the originating master ref auto-updates
  atomically (no Update-References modal, because the old ref is already dead); (b) normal edit of a healthy passage →
  new version + Update-References modal, no auto-mutation. State that remake does NOT trigger the Update-References
  modal.

  H5. Cross-passage numbering derivation is unspecified (collides with Reading V2 contract)

  - Issue: Reading V2 contract: "numbering is section-scoped + assembly-derived for full tests" and results store
  displayNumber. A ref-only composition has no embedded document, so displayNumber for each interaction must be computed
  at composition/assignment time from ordered passage refs. Neither Part 2 nor PRD-0054 says who computes it, when, or
  how it's frozen into the projection/result.
  - Evidence: Part 2 §9.1 lists "numbering metadata" with no algorithm; §9.3 frozen projection lists "passage refs" but
  not a resolved numbering map. PRD-0054 §7.10 numbering review ("auto-renumber from this passage forward") implies a
  renumber engine that is never specified.
  - Why it matters: Result review and student runtime both depend on stable per-interaction display numbers.
  Reorder/remove/replace changes them. Without a defined assembly-numbering service, juniors will compute numbers
  inconsistently across runtime, result review, and the numbering-review modal.
  - Affected: Part 2 §9.1/§9.3, Phase 6; PRD-0054 §7.10.
  - Correction: Add a "Composition Numbering" data/algorithm section: define the assembly numbering function (input:
  ordered passage refs + per-passage question counts; output: interactionId → displayNumber map), state it is frozen
  into the assignment projection and copied into results, and define exactly what "auto-renumber from this passage
  forward" recomputes.

  H6. "Publish commit audit" inside all-or-nothing publish conflicts with existing audit design

  - Issue: Part 2 FR-PUBLISH-5/6 make the publish commit audit part of the atomic all-or-nothing write set. The existing
  auditService.logAuditEvent is fire-and-forget (logAuditEventAsync(...).catch(...), separate audit_logs ref).
  - Evidence: auditService.ts:69–90 (async, swallowed errors); Part 2 FR-PUBLISH-5 lists "publish commit audit"
  alongside the atomic write set.
  - Why it matters: A junior will either (a) bolt audit into the RTDB multi-location update (changing audit
  semantics/rules), or (b) leave audit fire-and-forget and silently violate "all-or-nothing." PRD-0054 §9.4 also demands
  append-only audit, which the current swallow-errors writer doesn't guarantee.
  - Affected: Part 2 FR-PUBLISH-5/6; PRD-0054 §7.14, §9.4.
  - Correction: State whether audit is inside or outside the atomic boundary. Recommended: audit is best-effort outside
  the atomic publish (publish success does not depend on audit write), and FR-PUBLISH-5 should not list audit as part of
  the atomic set. Separately require audit_logs rules to be append-only (no update/delete).

  H7. Frozen composed projection storage + RTDB/Firestore consistency is undefined

  - Issue: Part 2 §9.3 says a "composed student-safe projection" is saved at assignment time, but never says where
  (which RTDB path), nor how it stays consistent with the Firestore homework_assignments doc that points to it.
  - Evidence: Part 1 tasklist line 144/146 (catalog+projections in RTDB, homework in Firestore). Part 2 §9.3 lists
  projection contents but no path. The Part 2 tasklist rollback note (line 386) correctly warns "RTDB multi-location
  update does not make Firestore writes atomic" — but the PRD itself provides no resolution.
  - Why it matters: Assignment creation now spans two stores (Firestore assignment + RTDB frozen projection). If the
  projection write fails after the assignment doc commits, students launch into a missing projection — exactly the
  FR-ASSIGN-10 "block launch" case, but silently created. Junior needs the ordering/recovery rule.
  - Affected: Part 2 §7.8, §9.3, Phase 6.
  - Correction: Define the frozen-projection RTDB path (e.g.,
  reading_v2/projections/assignment_payloads/{assignmentId}:{compositionVersionId}), define write ordering (projection
  first, then assignment doc references it), and define the launch-time fail-closed behavior when the projection is
  absent.

  H8. Auto V4 anchor-safety not carried into the split-on-publish

  - Issue: Part 2 first-publish splits an Auto-V4 full doc into N passage materials. Auto V4's hardened invariant
  forbids duplicate anchorIds and degrades structured layouts. Splitting must preserve per-passage anchor/interaction
  integrity; not mentioned.
  - Evidence: Auto V4 contract (reading-v2-auto-v4-provider-review-contract.md, anchor-foundation tasklist) defines
  registerStructuredLayoutAnchor / duplicate-structured-layout-question. Part 2 §7.2 publish requirements list outputs
  but no anchor-integrity validation per split passage.
  - Why it matters: A multi-passage Auto-V4 import that passes whole-doc validation could produce an
  individually-invalid passage material after split (e.g., anchors referencing a stimulus now in a different passage),
  crashing single-passage Studio later.
  - Affected: Part 2 §7.1/§7.2; references PRD-0048 anchor foundation.
  - Correction: Add FR-PUBLISH requiring each extracted passage to independently pass canonical anchor/interaction
  validation before publish commits; block split with a typed issue if any passage is individually invalid.

  2. Archived-master surface: PRD-0054 adds an Archive subtab to the Reading Passage tab only. Master delete uses soft

  inherits master visibility (FR-STUDIO-REMAKE-8); cloned passage defaults private (FR-CLONE-9); split passage = ?
  4. Public master referencing a now-private passage: FR-EXISTING-21 blocks publishing public with private refs, but a
  teacher can later change a passage to private. Does the public master become broken, hidden, or leak? Undefined
  (security-relevant).
  5. Broken-status recompute on restore/archive: who recomputes cached hasBrokenRefs on master/Book index rows when a
  passage is archived or restored? PRD-0054 §9.2 stores the flag but no invalidation owner (tasklist allows "modal-only
  detection" as deferral — but then card badges go stale).
  6. "Student started" authoritative signal (FR-ASSIGN-6): tasklist flags this (line 385) but the PRD asserts the
  capability without naming the source (submission doc? attempt doc? session state?). Must be defined, not approximated
  from UI.
  7. Duplicate similarity formula (PRD-0054 FR-DUP, threshold 80%): tasklist correctly flags formula is unspecified.
  Also: what is the "searchable text summary" index that avoids full-canonical scans during typing? No such index exists
  today.
  8. New-tab cross-tab refresh: single-passage Studio opens "in another browser tab." How does the Edit Test Modal /
  parent learn the passage published so it can refresh ref status? No cross-tab signal defined (and "new tab" is hostile
  on tablet/phone — see Rule Conflicts).
  9. Numbering engine (H5): the assembly-numbering function and its freeze points.
  10. Duplicate guard on auto-split (the original bug): the Codex session that spawned Part 2 was about passages
  auto-appearing on import of "Cambridge 20 Test 1," and the original decision was "a new reading passage will be made
  if not duplicated (compare dup % then confirm)." Part 2 FR-PUBLISH-1 creates one passage per passage with no dedupe.
  Re-importing the same Cambridge test creates duplicate passages silently. This is a missing requirement that traces
  directly to the founding use case.

  the whole doc.
  - Reading V2 publish pipeline: removing embedded document from master writes while keeping legacy compatibility reads
  (Part 2 FR-PUBLISH-8); verified document still threaded through writes — this is the load-bearing change.
  - Composition-first masters: numbering derivation (H5); visibility of split passages (#3).
  - Archive/restore: stale hasBrokenRefs recompute (#5); archived-master surface (#2); restore "same id/version"
  un-breaking refs requires index rebuild from canonical metadata (tasklist rollback note line 448).

  across two materials.
  - Book repair: Book refs may point to materials by id without version (verify materialBooks.service ref shape before
  assuming version-pinned broken detection works); 3-tab modal contract must be preserved (0054 tasklist Phase 4).
  - Duplicate detection: no similarity engine and no searchable-text index exist; threshold 80% with "body and question
  text equally" needs a concrete formula + a non-scanning data source.
  - Audit trail: existing auditService enum lacks archive/restore/repair actions and is fire-and-forget (H6);
  append-only rule unverified on audit_logs.
  - Assignment freeze: RTDB/Firestore split (H7); authoritative "started" signal (#6).
  - Result review: depends on frozen numbering map + frozen passage snapshots; must survive source archive (covered) and
  master deletion (covered).
  - Security rules: new composed-projection path; public-master-with-private-ref drift (#4).
